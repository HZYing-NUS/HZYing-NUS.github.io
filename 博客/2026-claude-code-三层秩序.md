# Claude Code 三层秩序：.claude、CLAUDE.md 与 skills

装完 Claude Code 的那个晚上，我做的第一件事不是写代码，是在自己 Mac 的家目录里翻出了一个叫 `.claude` 的文件夹。

它默默地就出现在那儿了。我没创建过它。我也没下载过它。它就像一个新来的同事，自己找了个工位坐下，把行李往那一搁，开始办公。

我盯着它看了一会儿，心里冒出一个问题：你是谁？你住我家了？你不走了？

后来我才搞清楚——这个 `.claude` 不是只有一个，它在我电脑里还有同名兄弟；和它一起出现的还有 `CLAUDE.md` 这个文件、还有一个叫 `skills` 的文件夹。这三样东西分别住在哪儿、各管哪一片、谁能压过谁，决定了 Claude Code 到底是「一个时不时帮你写两行代码的玩具」还是「一个长期能用的、记得你脾气的搭档」。

很多新手装完 Claude Code 后用了三个月还是只会把它当 ChatGPT 用，根本原因不是不会写 prompt，是没看懂这套**目录结构里的秩序**。

这篇我用一句话先把判断给你，再用结构慢慢拆。

## 一句话判断：Claude Code 是一个有「上岗手册」的员工

把这件事翻译一下，你就秒懂了：

Claude Code 这个 AI，**不是一个一次性回答你问题的聊天机器人，是你雇来的一个员工**。员工要长期干活，就要有三样东西：

- **档案柜**：放他个人物品、工牌、过往记录的地方——`.claude` 这个文件夹
- **上岗手册**：告诉他「这家公司怎么运作、不能干什么、客户叫什么名字」——`CLAUDE.md` 这个文件
- **技能证书**：他会哪些活儿、每种活儿的标准流程是什么——`skills` 文件夹里一个个的 SKILL

而你电脑里有两个层级的「办公场所」：

- **你家**（用户主目录）：你这个人本身的常驻空间，所有项目都从这里看一眼
- **公司**（项目根目录）：某一个具体项目的工作现场，只有进了这个项目才生效

这个员工每次开始干活之前，**会先去你家拿一份手册（全局规矩），再去公司拿一份手册（项目规矩），把两份叠起来照着干**。技能证书也是一样：你家档案柜里有的他都会、公司档案柜里有的他在公司里也会。

到这里你已经把 80% 的核心讲清楚了。下面把每一件事拆细。

## 第一层：.claude 文件夹——它到底是谁、住哪儿、谁建的

`.claude` 是一个**隐藏文件夹**。所谓「隐藏」，意思是 Mac Finder 默认不显示它（按 `Cmd + Shift + .` 才看得到），Windows 资源管理器也是默认藏的。这是它名字前面那个点的作用——按 Unix 习惯，点开头表示「这是配置文件，平时别动」。

它有两个能合法出现的位置：

**位置一：你的家目录下**——`~/.claude/`

`~` 在终端里就代表「当前这个用户的家」。Mac 上是 `/Users/你的用户名/`，Windows 上是 `C:\Users\你的用户名\`。这里的 `.claude` 是**全局的**，不管你后面打开哪个项目都会先读它。

**位置二：某个项目的根目录下**——`项目文件夹/.claude/`

只有在这个项目里干活时才生效。你换一个项目，这个 `.claude` 就和这一次工作无关了。

它怎么生成的？不是你建的。**是 Claude Code 第一次跑起来的时候自己建的**。你装完 `claude` 命令、第一次在终端敲 `claude` 进入对话、它就把家目录里的 `~/.claude` 自动初始化好。等你第一次在某个项目里用它干活、又在那个项目根下建一个 `.claude`。

我自己机器上是这样的——这是我刚刚 `ls` 出来的真实状态：

```
全局：/Users/huangziying/.claude/
├── CLAUDE.md         （我自己的全局上岗手册）
├── settings.json     （全局设置）
├── sessions/         （历史对话）
├── projects/         （项目元信息）
├── plugins/
└── 还有十几个系统目录

项目：/Users/huangziying/Documents/黄梓颖的第二大脑/.claude/
├── skills/           （这个项目专属的 12 个 skill）
├── agents/
└── commands/
```

注意一个细节：**全局 `.claude` 装的是 Claude Code 这个工具的运行时数据**（历史、会话、缓存），所以你看到一堆系统目录；**项目 `.claude` 装的是你为这个项目准备的扩展**（skill、命令、子代理），所以它干净得多，只有你想让 AI 做的事情。

**子目录里能不能再放 `.claude`？**

技术上能塞进去，但 Claude Code 不会去读它。它只认两个位置：你家、和当前项目根。在子目录里再建一个 `.claude`，等于在公司茶水间里又支了一个工位——没人知道你在那儿坐着，没人会过去找你干活。

所以一个朴素的纪律：**`.claude` 只放两个地方，全局和项目根**。其他位置都是误操作。

## 第二层：CLAUDE.md——上岗手册的三层放法

如果说 `.claude` 是档案柜，那 `CLAUDE.md` 就是钉在档案柜门上的那张「上岗手册」。员工每次开工前都会撕下来读一遍。

它能放在三个地方，每一层有自己的角色：

**第一层：全局——`~/.claude/CLAUDE.md`**

写的是**你这个人的偏好**。你叫什么、希望它怎么称呼你、回复风格要什么样、代码注释用中文还是英文、不要写哪些废话。这一层和具体项目无关，**所有项目都共享**。

举个我自己的例子：我家目录的 `~/.claude/CLAUDE.md` 只有 1.7KB，里面就写了几条——「叫我梓颖」「回复中文优先」「中文用中文标点」「代码命名尽量中文 / 拼音」「不写不必要的注释」。这就是你这个人的「人格设定」。所有项目都从这里继承。

**第二层：项目根——`项目文件夹/CLAUDE.md`**

写的是**这个项目的规矩**。这个项目的目录结构、命名规则、有哪些不能动的红线、新内容应该落在哪里、特殊词汇怎么解释。这一层只在你打开这个项目的时候生效。

我的知识库（也就是这个 vault）项目根的 `CLAUDE.md` 是 12KB，**比全局那份大了 7 倍**。里面写满了：哪些目录是只读的、新内容默认落点、命名规则速查、Skill 调度规则、Inbox 巡检规则……这些东西换一个项目就完全不适用，不该污染全局。

**第三层：项目子目录——`项目文件夹/某个子文件夹/CLAUDE.md`**

写的是**这个子目录的特例**。比如某个特别敏感的文件夹想加额外的规矩、某个子模块有自己独立的命名风格。

子目录的 `CLAUDE.md` 不是必备的，多数项目压根用不到。但它存在的意义是：**当 AI 在这个子目录里干活的时候，它会临时把这层规矩叠加上**。

**叠加顺序你要记住一句话**：从大到小依次叠加，从远到近依次覆盖。

也就是说，AI 进入项目里某个子文件夹时，它脑子里同时装着：

```
[全局 ~/.claude/CLAUDE.md]
        ↓ 叠加
[项目根 CLAUDE.md]
        ↓ 叠加
[当前子目录 CLAUDE.md]
        ↓
        干活
```

冲突的时候，**近的赢远的**。子目录说「这里的命名用英文」，就算项目根写着「全用中文」，也按子目录来。这是配置系统里非常经典的「就近原则」，工程上把它叫**作用域分层**——全局作用域、项目作用域、局部作用域，越靠近你正在做的事，优先级越高。

新手最常见的两个错误，到这里就能讲清了：

第一个错误：**把项目规矩写到全局里去**。结果是每次开新项目都得手动改回来，或者 AI 在新项目里坚持按上一个项目的规矩干活，怎么劝都不听。

第二个错误：**把全局偏好写到每个项目里**。结果是 10 个项目里有 10 份 `CLAUDE.md` 都在重复「叫我梓颖、回复中文」这种话。改一次得改 10 次。

`CLAUDE.md` 就是一个有层级的备忘录系统。**写之前先问一句：这条规矩离开这个项目还有效吗？有效就放全局，无效就放项目**。

## 第三层：skills——可调用的技能包，是文件夹不是文件

`CLAUDE.md` 解决的是「**这个员工怎么和我说话、不能干什么**」，但它没解决一个更具体的问题：「**遇到具体的活儿，他知不知道标准操作流程？**」

这就是 skills 干的事。

skills 不住在 `CLAUDE.md` 旁边，它住在 `.claude` 文件夹里——`/.claude/skills/`。

**它和 `CLAUDE.md` 最大的不同是：skill 不是一个文件，是一个文件夹**。

每个 skill 是 `skills/` 下面的一个独立子目录，里面**至少有一份 `SKILL.md`**，可能还附带一些脚本、模板、参考资料。Claude 在你提任务时，会先扫一眼有哪些 skill 可用、看每个 skill 的简短描述，**判断这次任务是否要调用哪个 skill 的标准流程**。

它的两个层级和 `.claude` 一样：

- **全局 skill**：`~/.claude/skills/`——所有项目都能调
- **项目 skill**：`项目根/.claude/skills/`——只有这个项目里能调

我这个知识库项目的 `.claude/skills/` 里现在长这样（真实状态，刚 `ls` 出来）：

```
.claude/skills/
├── ai-newsletters       （AI 资讯精选流程）
├── ai-products          （AI 产品周报流程）
├── archive              （归档流程）
├── ask                  （快速问答模式）
├── brainstorm           （头脑风暴流程）
├── json-canvas          （Canvas 文件创建）
├── kickoff              （把灵感变成项目笔记）
├── obsidian-bases       （Bases 视图制作）
├── obsidian-markdown    （Obsidian Markdown 写作）
├── parse-knowledge      （知识库整理）
├── research             （深度研究流程）
└── start-my-day         （每日启动流程）
```

12 个 skill。每一个都是一个文件夹，里面是一份对应任务的标准操作手册。

skill 和「在对话里写一段长 prompt」最大的区别：**skill 是写一次、长期生效；prompt 是临时输入、用完就忘**。

你每次遇到「写一篇公众号文章」这种任务，不再需要重新写半小时的指令；你只要让 AI 调用 `skill-AI公众号图文创作`，它会按里面预先写好的六个步骤跑，从拆对标、读者画像、合成写作 prompt、生成初稿、人机精修、到出封面图，一条线串到底。

这就回到了系统科学最朴素的一条原理：**重复发生的事，要从「每次重做」升级成「一次定义、长期复用」**。skill 就是把你和 AI 的协作从一次性对话，沉淀成可调用的资产。

什么场景下要写一个 skill？

简单的判断：**同一段指令你已经粘贴第 3 次了，就该把它写成 skill**。第三次是一个心理阈值——前两次还能忍，第三次说明这是高频任务、有标准化收益。

放全局还是放项目？

判断也很简单：**这件事换个项目还要做吗？要，就放全局；不要，就放项目**。

「写公众号图文」这件事我所有项目都不会做（我只在这个 IP 项目里做），所以它放在项目里。但「把代码改完跑一遍 lint」这种事所有代码项目都要做，那它该放全局。

## 一张表，把三件套和三层位置交叉一次讲完

到这里所有概念都讲过了。最后用一张表把它们串起来——这张图你存下来，遇事查一查不会再混：

| 位置             | `.claude/`             | `CLAUDE.md`                        | `skills/`               |
| ---------------- | ---------------------- | ---------------------------------- | ----------------------- |
| **全局**（`~/`） | ✅ 工具自己建          | ✅ 写你这个人的偏好                | ✅ 所有项目通用的技能   |
| **项目根**       | ✅ 项目专属配置        | ✅ 写这个项目的规矩                | ✅ 项目专属的技能       |
| **项目子目录**   | ❌ 不会被读            | ✅ 局部例外覆盖                    | ❌ 不会被读             |
| **谁建的**       | Claude Code 自动建     | 你手动建 / `/init` 命令生成        | 你手动建 / 让 AI 帮你建 |
| **作用范围**     | 当前作用域内的扩展容器 | 当前作用域的规矩                   | 当前作用域可调用的流程  |
| **生效叠加顺序** | —                      | 全局 → 项目根 → 子目录（近覆盖远） | 全局 + 项目（并集）     |

**两条容易记错的细节再点一次**：

1. `.claude` 和 `skills` 都不在子目录里出现。子目录唯一能放的是 `CLAUDE.md`。
2. `CLAUDE.md` 是「叠加」逻辑（多份会一起读、近的覆盖远的），`skills` 是「并集」逻辑（全局有的 + 项目有的，都能用）。

## 新手最容易踩的四个坑

**坑一：把 README 当 CLAUDE.md 写**

`CLAUDE.md` 不是给人看的项目介绍，是给 AI 看的工作手册。**写「这是什么项目」是浪费——AI 看了文件结构就知道；写「这个项目里我不希望它做什么」才是它该读的**。

**坑二：每个项目都重复写「叫我梓颖、用中文」**

这种和项目无关的偏好，写一次到 `~/.claude/CLAUDE.md` 就行。复制 10 份到 10 个项目，等于每改一次就要改 10 个文件。

**坑三：在子目录里建 `.claude`**

不会生效。如果想在子目录里加规矩，建 `子目录/CLAUDE.md`，不要建 `子目录/.claude/`。

**坑四：把所有 skill 都堆在全局**

全局塞 50 个 skill 的代价是：每次开新对话 AI 都要扫一遍这 50 个简介、判断哪个该用，浪费上下文也容易选错。**只有真正跨项目通用的才放全局，其他统统放项目里**。

## 一句话收尾

理解 Claude Code 的层级，本质上不是理解一个工具，是理解一种**配置作用域**的工程思维：

> 让 AI 长期可控的关键，不是把所有规矩塞给它，是把规矩按「作用范围」分层、放对位置。

全局放的是「你这个人」，项目放的是「这件事」，子目录放的是「这个角落」。三层各管各的，叠在一起就是一个稳定可演化的工作系统。

我自己用 Claude Code 的体感是：**配置写得越分层，AI 的输出就越稳；越扁平，越容易出现「这事它前几天还会做，今天怎么忘了」的诡异感**。这不是 AI 在偷懒，是你给它的工作环境本身就是混乱的——它每天上岗都拿到一份矛盾的手册，它当然会精神分裂。

把 `.claude`、`CLAUDE.md`、`skills` 这三件套放对位置，相当于你给这个员工搭了一个**有秩序的办公空间**。剩下的事情，他会自己长起来。
