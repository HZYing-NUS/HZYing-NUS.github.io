# 一个做产品的人，我给 Claude Code 配了专家团、项目经理和纪律委员

这段时间，我一直在用 AI 编程做产品。

刚开始最兴奋的地方是：代码真的能跑出来。

你说一句需求，AI 给你写页面。
你贴一个报错，AI 帮你修。
你让它加个功能，它能一口气改好几个文件。

那种感觉很容易让人上头。

但上头一段时间之后，我发现了一个很现实的问题：

AI 编程不是不会写代码。
它的问题是，太容易失控。

你让它改一个按钮，它顺手重构半个项目。
你让它修一个 bug，它直接猜一个原因就开干。
你让它做一个功能，它写得很快，但测试、边界、验收全都飘在空中。

更可怕的是，它看起来一直很勤奋。

一直在改。
一直在解释。
一直在输出。

但你最后回头看，会发现项目并没有真正往前走多少。

这也是我后来特别强烈的一个感受：

**AI 是乘数，不是加数。**

你本来有一套清晰的工作流，它会把效率放大。
你本来就是混乱的，它也会把混乱放大。

所以我现在越来越不相信换一个更强的模型能解决所有问题。

模型当然重要。
但真正决定 AI 编程上限的，是你有没有给它配一套工作系统。

我现在用得最顺手的，是一个三件套：

**gstack，GSD，Superpowers。**

如果用公司里的角色来比喻，它们分别是：

- gstack：专家团队
- GSD：项目管家
- Superpowers：开发纪律

这三个东西拼起来，才是我理解里比较完整的 AI 编程工作流。

不是让 AI 更像一个聪明码农。
而是让它更像一个被系统管理起来的产品团队。

---

## 一、gstack：给 AI 配一个外部顾问团

以前我用 AI 写代码，最大的问题是：所有判断都压在一个模型身上。

它既要理解需求。
又要拆技术方案。
又要写代码。
又要审查自己写得对不对。
还要判断有没有安全问题。

这其实很离谱。

放到真实团队里，你不会让一个人同时当产品经理、架构师、前端、后端、测试、代码审查人。

但很多人用 AI 编程时，真的就是这么用的。

一个 Claude Code，从头干到尾。
干错了，再让它自己解释为什么错。
解释完，再让它自己修。

这就像让一个学生自己出卷、自己考试、自己判分。

gstack 解决的，就是这个问题。

它的核心价值不是帮你多写几行代码，而是给 AI 编程引入一组专家视角。

你可以把它理解成一个外部顾问团。

当你要做方向判断时，它可以帮你讨论方案。
当你写完代码时，它可以帮你审查质量。
当你不确定技术路线时，它可以从不同角色给你反馈。

它不是替你做决定。
它是逼你在开工前、合并前、发布前，多经过几轮更高质量的思考。

这点对一个人做产品尤其重要。

因为一个人最大的问题，不是手不够。
是没有人拦你。

没人提醒你这个需求其实不该做。
没人提醒你这个实现以后会埋坑。
没人提醒你这段代码只是看起来能跑。

AI 编程最危险的地方，也在这里。

它会让你获得一种虚假的速度感。

你以为自己在快速推进，其实只是更快地把错误写进项目里。

gstack 的意义，就是在速度前面加一道判断。

---

## 二、GSD：给项目配一个项目经理

第二个工具是 GSD，全称是 Get Shit Done。

名字很粗暴，但它解决的问题很具体：

**项目推进。**

很多人用 AI 编程时，会卡在一个地方：

不是不会写代码，而是不会把一个产品拆成一条可执行的路径。

今天想加登录。
明天想加支付。
后天又觉得首页不够好看。
中间冒出来一个 bug，顺手修一下。
修着修着，又让 AI 重构目录。

最后项目变成一团毛线。

每一段都像在前进，但没有一条明确的主线。

我以前也很容易掉进这个坑。

尤其是 AI 速度太快之后，你会忍不住一直加东西。
它让你产生一种错觉：反正实现成本很低，那就都试试。

但产品不是功能堆出来的。

产品是靠取舍推出来的。

GSD 对我最大的帮助，是把 AI 编程从聊天式推进变成项目式推进。

它会更强调阶段、任务、验收标准和进度状态。

你不再只是对 AI 说：

“帮我做一个功能。"

而是让它进入一个更清晰的项目流程：

这个项目要解决什么问题？
当前阶段要完成什么？
每个任务的完成标准是什么？
哪些事情已经 done？
哪些事情还卡着？
下一步应该先做什么？

这听起来很基础。

但越基础的东西，越容易被 AI 编程的新鲜感冲掉。

很多 AI 项目死掉，不是因为代码写不出来。
是因为没人管进度。

没人管进度，项目就会自然扩散。
需求扩散。
文件扩散。
上下文扩散。
最后连你自己都不想打开。

GSD 像一个项目经理。

它不一定替你做最难的技术判断。
但它会把项目拉回现实：

现在到底在做什么？
做完的标准是什么？
下一步是什么？

一个人做产品，很需要这个角色。

因为当你既是老板、产品、开发、运营，又是测试时，你最容易缺的不是执行力。

你缺的是一个冷静的推进系统。

## 三、Superpowers：给 AI 加开发纪律

第三个是 Superpowers。

如果说 gstack 像专家顾问团，GSD 像项目经理，那 Superpowers 更像纪律委员。

它解决的是另一个特别要命的问题：

AI 太容易跳过正确流程。

遇到 bug，它喜欢直接猜。
写新功能，它喜欢直接开工。
改完代码，它喜欢直接说完成了。
测试没跑，边界没验，甚至有时候连自己改了什么都没讲清楚。

这不是某一个模型的问题。

这是 AI 协作里天然会发生的问题。

因为 AI 的默认倾向是：给答案。

但开发里，很多时候最重要的不是答案，而是流程。

比如调 bug。

一个好的工程师不会一上来就改代码。
他会先复现问题，观察现象，提出假设，验证假设，再做最小改动。

但 AI 很容易跳到最后一步：

“我知道了，我来修。"

这句话听起来很爽。
但很多灾难就是从这里开始的。

Superpowers 的价值，是把一些开发纪律变成自动触发的工作方式。

比如：

写功能时，先想测试。
遇到问题时，先系统化调试。
准备结束时，先做完成验证。
需要审查时，先请求代码 review。

它不只是一个工具包。
更像是给 AI 套上了一组行为规范。

这件事很重要。

因为 AI 编程真正难的地方，不是让它更努力。
是让它在该停的时候停下来。

该先写测试，就别急着写实现。
该先复现问题，就别急着猜原因。
该跑检查，就别急着宣布完成。

很多时候，效率不是来自更快。
效率来自少返工。

Superpowers 就是在减少返工。

它把那些你本来需要反复提醒 AI 的事情，变成一套更稳定的默认动作。

这对我来说特别关键。

因为我不会把自己伪装成资深工程师。

我真正需要的，不是一个永远顺着我说可以的 AI。
我需要的是一个会在关键节点拦我一下的系统。

---

## 这三个工具为什么要一起用？

单独看，它们每一个都挺有用。

但真正的价值，是它们拼在一起之后，形成了一个闭环。

gstack 管判断质量。
GSD 管项目推进。
Superpowers 管开发纪律。

一个负责想清楚。
一个负责往前推。
一个负责别乱来。

这三个角色缺一个，AI 编程都会偏。

只有 gstack，没有 GSD，你会讨论很多，但项目不一定往前走。
只有 GSD，没有 Superpowers，你会推进很快，但质量可能失控。
只有 Superpowers，没有 gstack，你会流程很规范，但方向可能一开始就是错的。

所以我现在越来越觉得，AI 编程不是“人 + AI"这么简单。

更准确地说，它是：

**人 + AI + 工作流。**

人负责判断。
AI 负责执行。
工作流负责约束。

这也是我最近做产品时最大的变化。

我不再把 AI 当成一个万能员工。
我开始把它放进一个组织结构里。

该有专家，就配专家。
该有项目经理，就配项目经理。
该有开发规范，就配开发规范。

你会发现，AI 不是突然变聪明了。

是它终于不再裸奔了。

## 安装方法

下面是我目前查到的安装口径。工具更新很快，安装前建议你再点开官方仓库确认一次。

### 1、安装 gstack

gstack 的官方仓库是 `garrytan/gstack`。

如果你用的是 Claude Code / Codex / Gemini CLI 一类的 AI 编程工具，可以按仓库说明安装。

公开页面里给出的安装示例之一是：

```bash
git clone https://github.com/garrytan/gstack.git ~/.codex/skills/gstack
```

如果你用的是支持 AgentSkill 的工具，也可以用：

```text
/learn @garrytan/gstack
```

安装后，它更像是一套可调用的专家协作流程。
你可以在做方案讨论、代码审查、测试质量检查时调用它。

### 2、安装 GSD

GSD 的官方仓库是 `gsd-build/get-shit-done`。

常规安装命令是：

```bash
npx get-shit-done-cc@latest
```

如果你想给 Claude Code 做全局安装，可以用：

```bash
npx get-shit-done-cc --claude --global
```

安装后，重启 Claude Code，在项目目录里运行：

```text
/gsd:help
```

新项目可以从：

```text
/gsd:new-project
```

开始。

我的理解是，GSD 最适合在准备正式做一个产品 / 功能 / 项目时使用。
它会比普通聊天更像一个项目推进系统。

### 3、安装 Superpowers

Superpowers 的官方仓库是 `obra/superpowers`。

Claude Code 插件安装方式是：

```text
/plugin install superpowers@claude-plugins-official
```

安装后，它会提供一系列开发流程类 skills。

比如系统化调试、测试驱动开发、完成前验证、代码 review 等。

这类工具一开始可能会让你觉得麻烦。
但它的价值恰恰在这里。

它不是让 AI 更快开工。
它是让 AI 不要乱开工。

对长期做产品的人来说，这比快一点更重要。

---

## 我的建议：别一次装完就开始狂用

如果你刚开始接触这套东西，我不建议你一口气把所有流程都打开。

那样很容易变成另一种工具囤积症。

可以按这个顺序来：

第一步，先装 Superpowers。
让 AI 养成调试、测试、验证的基本纪律。

第二步，再装 GSD。
把一个具体项目拆成任务，开始管进度。

第三步，最后加 gstack。
在关键决策和代码审查节点，引入外部顾问团视角。

先把一个小项目跑完。

不要追求完美配置。
不要一上来就搭一个巨复杂的工作台。
也不要把时间都花在研究工具本身。

工具的意义，是把产品往前推。

如果一个工具没有让你的项目更清晰、更稳定、更接近发布，它暂时就不重要。

我现在越来越相信一件事：

**AI 时代真正拉开差距的，不是谁收藏了更多工具，而是谁能把工具组织成系统。**

gstack、GSD、Superpowers 这套三件套，对我来说就是这样一个系统。

它让我从让 AI 帮我写代码，慢慢切到让 AI 在一个产品团队结构里工作。

这中间的差别很大。

前者靠兴奋感。
后者靠秩序感。

而一个人做产品，最缺的往往不是更多能力。

是一个能把能力稳定释放出来的系统。
