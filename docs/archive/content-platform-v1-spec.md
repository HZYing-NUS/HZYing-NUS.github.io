# 基于 ShipAny 的 AI Web SaaS 一站式出海资源平台 SPEC

> 状态：已归档。
>
> 本文档记录 WebTools 从静态个人站迁移为 ShipAny 内容平台的 V1 需求与历史决策。主体功能已基本完成，本文档不再作为当前开发规格。
>
> 后续的 AI 助手、项目记忆、Skill、联网搜索、模型供应商、Credit 与付费体系，参见 `docs/specs/webtools-ai-assistant-v1-spec.md`。

## Context

当前项目是梓颖的个人静态网站，主要通过 GitHub Pages 部署。现有核心结构为：

- `index.html`：主页、样式、语言切换、暗色模式、证书灯箱、打印简历、右下角「问问 AI」。
- `内容配置.js`：主页内容数据源。
- `博客索引.js`：博客列表数据源。
- `博客.html`：博客详情页模板。
- `博客/*.md`：博客正文。
- `图片/*`：头像、二维码、证书、项目证明等图片资源。
- `ai代理/worker.js`：Cloudflare Worker AI 代理，当前使用 DeepSeek，并维护一份手写的 `个人资料` 知识库。

梓颖希望把它升级为全栈内容平台，并采用 ShipAny Starter 作为基础，而不是从零搭建 Next.js 项目。ShipAny 的定位是面向 AI 产品快速上线的 Next.js starter，已内置多语言、登录鉴权、数据库、支付、积分、部署配置、管理后台设置等能力。其中部分能力适合复用，部分能力在本项目 V1 中需要弱化或移除。

参考站点：

- ShipAny 官网：`https://shipany.ai/zh`
- ShipAny Docs：`https://docs.shipany.ai/zh/shipany-next`
- 参考内容平台：`https://aichuhai.dev/`

已从 ShipAny 文档确认的关键事实：

1. ShipAny Next 是基于 Next.js 的 starter。
2. 鉴权基于 `better-auth` + Drizzle Adapter。
3. 鉴权配置位于 `src/core/auth/index.ts`。
4. 鉴权请求由 `/api/auth/[...all]` 处理。
5. 支持邮箱密码登录、Google 登录、GitHub 登录。
6. OAuth 配置可在管理后台 `Settings → Auth` 中配置，并存储于 `config` 表；同名环境变量可作为兜底。
7. 会话存储在 `session` 表，以 httpOnly Cookie 下发。
8. `user` 表包含扩展字段，如 `utmSource`、`ip`、`locale`。
9. 数据库使用 Drizzle，支持 PostgreSQL / MySQL / Turso / D1 等不同 provider。
10. Vercel 部署走标准 Next.js 流程：导入仓库、配置环境变量、部署。
11. 数据库迁移需要单独执行：`pnpm db:generate && pnpm db:migrate`。
12. Docker 部署已有多阶段 Dockerfile。
13. Cloudflare Workers 部署已有 `wrangler.jsonc`、`nodejs_compat`、D1 绑定等配置，但本项目 V1 优先 Vercel + Neon，不走 Workers 部署。

## Problem Statement

当前网站的核心问题不是「缺少一个更现代的技术栈」，而是：梓颖在做 AI Web SaaS 网站和出海产品时，会长期遇到大量参考网站、工具、模板、插件、Skill、MCP、Starter、基础设施服务和运营资源，但现有静态站无法把这些资源按 AI Web SaaS 创业流程组织成一个随查随用的一站式资源平台。

具体问题：

1. 资源分散在浏览器收藏夹、聊天记录、临时文档、网站页面和个人经验中，无法被系统分类、搜索、复用，也无法围绕「从想法到上线运营」的完整流程串起来。
2. 网站搭建、原型设计、UI 参考、前端实现、AI 模型选择、部署上线、域名、登录、SEO、增长运营等阶段缺少统一资源地图。
3. Skill、MCP、Chrome 插件、Starter 模板、组件库、模型榜单、需求发现网站等资源类型差异很大，当前个人站没有合适的数据模型承载。
4. 当前博客仍嵌在个人主页中，不利于独立沉淀文章、教程、复盘和后续轻互动。
5. 当前「关于我」内容有价值，但仍偏静态展示，后续应作为新站的可信度与个人品牌模块迁移。
6. 当前「问问 AI」与站点内容割裂，需要手动同步资料，未来容易过期，也无法围绕资源库提供来源明确的问答。
7. 新增内容需要改文件、维护索引、重新部署，不适合长期高频收纳和更新。
8. 如果从零搭建，会重复实现登录、数据库、后台设置、多语言、部署等通用能力，浪费时间。

因此，V1 的核心目标是：基于 ShipAny 快速搭建一个可部署、可登录、可管理、可搜索、可双语展示的 AI Web SaaS 一站式出海资源平台，同时独立博客、迁移关于我，并保留后续社区互动的扩展空间。

## Proposed Solution

采用 ShipAny Starter 作为新项目底座，在其既有能力上做减法和定制化，而不是从零搭建。

### 总体方向

新站定位为：梓颖的 AI Web SaaS 一站式出海资源平台。

它的核心不是传统个人主页，也不是泛泛的博客站，而是一个面向 AI Web SaaS 创业者的一站式资源平台，围绕需求发现、产品设计、前端开发、模型选择、部署上线、域名邮箱、登录鉴权、支付订阅、SEO、增长运营和数据分析等阶段，系统整理参考网站、工具、Chrome 插件、Skill、MCP、Starter、组件库、UI 模板、服务商、教程和实战经验。博客和关于我作为辅助模块，承接个人经验沉淀、可信度展示和长期个人品牌。

它不替代 Vercel、Namecheap、AITDK、Toolify、TrustMRR、MCP、Skill、Starter、组件库这些工具，而是把它们按 AI Web SaaS 创业流程组织起来，让用户能快速找到、理解、组合和使用。

V1 需要实现：

1. 完整迁移当前个人站内容。
2. 明确产品边界：不替代第三方工具和服务，而是按 AI Web SaaS 创业流程组织、解释、推荐和组合这些资源。
3. 建立以资源库为核心的内容体系，覆盖网站、工具、Chrome 插件、Skill、MCP、Starter、UI 模板、组件库、模型榜单和服务商。
4. 独立博客模块，迁移当前博客并支持后续原创文章、教程、复盘和经验总结。
5. 建立专题 / 合集能力，用于按建站流程和使用场景组织资源。
6. 通过后台管理资源、文章、专题、投稿、标签和分类。
7. 支持 Google 登录和投稿建议。
8. 支持全站双语。
9. 支持站内搜索。
10. 支持 AI Web SaaS 建站资源助手，并提供来源链接。
11. 部署到 Vercel，数据库使用 Neon PostgreSQL。

### V1 信息架构

参考 `aichuhai.dev` 的内容组织方式，但不复刻；本项目的核心是「AI Web SaaS 一站式出海资源平台」。

V1 页面结构：

1. 首页
   - 介绍平台定位：面向 AI Web SaaS 创业者的一站式资源地图和建站手册。
   - 展示精选资源、热门专题、最新文章、常用工具链。
   - 保留梓颖个人可信度入口，但不把个人主页作为首屏核心。

   - 每个资源应有简介、推荐理由、使用场景、链接、截图或图标。

3. 专题 / 合集
   - 按建站流程、使用场景或任务目标组织资源。

6. 关于我
   - 迁移当前个人站核心内容。

7. 搜索
   - 跨资源、专题、文章、关于我搜索。
   - 支持关键词、类型、阶段、标签、分类筛选。

8. AI 资源助手
   - 从当前右下角「问问 AI」升级为围绕资源库和站内内容的 AI Web SaaS 资源助手。

9. 管理后台

### 内容与媒体存储策略

#### 文章正文

V1 将文章正文以 Markdown 文本形式存入 Neon PostgreSQL，由后台管理。

这意味着：

1. 旧站 `博客/*.md` 会被导入数据库。
2. Markdown 格式仍然保留，但不再以 `.md` / `.mdx` 文件作为主要内容来源。
3. 页面读取文章时，从数据库查文章正文并渲染。
4. 后台可以直接新增、编辑、发布文章。
5. 搜索、AI 问答、投稿转正式内容都可以直接使用数据库内容。

#### 图片与附件

图片文件本体不建议直接存入 Neon PostgreSQL。

V1 推荐策略：

1. 图片文件本体先放在 Next.js 项目的 `public/` 目录下，例如 `public/images/`。
2. 数据库只保存图片 URL、alt、说明、归属内容、排序等元数据。
3. 页面通过数据库中的 URL 引用图片。
4. 后续图片量变大后，再迁移到对象存储，例如 Cloudflare R2、S3、Cloudinary 或 Vercel Blob。

不推荐把图片二进制或 base64 直接塞进 PostgreSQL，原因是数据库会膨胀，备份和迁移变慢，CDN 缓存也不方便。

### 轻互动与投稿建议

V1 的互动目标是形成友好的资源共建氛围，但不做完整社区。

优先做：

1. 资源推荐：用户推荐网站、工具、Chrome 插件、Skill、MCP、Starter、服务商等。
2. 纠错反馈：用户反馈链接失效、描述过期、分类错误。
3. 补充信息：用户补充使用经验、替代工具、价格变化。
4. 文章建议：用户推荐可写的教程、复盘、经验主题。
5. 专题建议：用户建议新的资源合集或建站流程清单。

V1 暂不做站内评论系统，但可以保留外部讨论入口，例如 GitHub Discussions、微信群、邮箱反馈或社交平台链接。后续如果资源库有稳定访问和投稿，再考虑站内评论、回复和用户主页。

### 鉴权与权限

基于 ShipAny 已有 `better-auth` 鉴权体系。

V1 登录策略：

1. 管理员登录：Google 登录。
2. 用户投稿：Google 登录。
3. 邮箱密码登录：底层可保留，但 V1 不作为主入口。
4. GitHub 登录：默认不启用。

权限边界：

1. 游客
   - 浏览公开内容。
   - 使用搜索。
   - 使用 AI 问答。

2. Google 登录用户
   - 提交投稿建议。
   - 后续可查看自己的投稿记录，V1 可选。

3. 管理员
   - 访问管理后台。
   - 管理资源、专题、文章、关于我内容。
   - 管理标签、分类、精选。
   - 审核投稿建议、纠错反馈和补充信息。
   - 管理 AI 引用状态。

管理员权限应通过管理员邮箱白名单控制，不能让所有 Google 登录用户访问后台。

### 管理后台

优先复用 ShipAny 管理后台与配置体系，但要围绕本项目内容模型扩展。

V1 后台能力：

1. 资源管理。
2. 专题 / 合集管理。
3. 文章管理。
4. 投稿建议、纠错反馈和补充信息审核。
5. 标签管理。
6. 分类管理。
7. 使用阶段管理。
8. 精选内容管理。
9. 发布状态管理。
10. 中英文内容管理。
11. AI 引用开关管理。
12. 关于我内容管理，至少支持迁移后的结构化展示。

ShipAny 原本与支付、价格、积分相关的后台设置，V1 应隐藏或不暴露给管理员主流程。

### 全站双语

V1 采用全站双语策略。

要求：

1. 中文和英文都有独立访问路径。
2. UI 文案支持中英文。
3. 资源、专题、文章、关于我支持中英文字段。
4. SEO 信息支持中英文。
5. AI 问答根据当前语言回答。
6. 迁移期允许某些内容只有一种语言，但必须有明确回退策略。

ShipAny 已有多语言能力，应优先复用，不重新造一套 i18n。

5. 分类筛选。
6. 中英文检索。

实现建议：先基于 PostgreSQL / Drizzle 做数据库搜索；如 ShipAny 已有搜索模块或命令菜单能力，优先复用 UI 和交互模式。

### AI Web SaaS 建站资源助手

当前 `ai代理/worker.js` 的能力需要升级，而不是原样迁移。

V1 目标：

1. AI 能基于站内资源、专题、文章、关于我回答。
2. 回答必须带来源链接。
3. 当前语言为中文时中文回答，英文时英文回答。
4. 找不到站内来源时明确说明没有找到相关内容。
5. 管理员可以控制哪些内容允许 AI 引用。
6. 不再维护 Worker 里的手写 `个人资料`。

实现建议：

1. V1 先使用数据库检索 + LLM 回答。
2. 从数据库查出相关资源、专题、文章的摘要、标题、URL、类型和使用阶段。
3. 将这些内容作为上下文传给模型。
4. 生成回答时附来源。
5. 后续再考虑 embedding、pgvector、向量检索。

DeepSeek 可先沿用，但需要抽象成 AI 服务层，避免和具体模型强绑定。

## Resolved Decisions

以下决策已确认，后续实现按这些默认方案执行：

1. ShipAny 原有付费、积分代码：V1 先隐藏入口和路由访问，避免大规模破坏 starter 结构；不进入主导航、首页、后台主流程和公开页面。
2. 图片存储：V1 图片文件先放 `public/images/`，数据库保存图片 URL、alt、说明、归属内容、排序等元数据；后续内容量变大再迁移对象存储。
3. 邮箱密码登录：V1 不作为主入口，只保留 ShipAny 底层能力。
4. GitHub 登录：V1 不启用。
5. 旧博客 URL：核心旧博客做跳转，降低历史链接损失。
6. AI 模型：先沿用 DeepSeek，但代码上抽象成可替换服务。
7. ShipAny 默认 landing page 模块：只保留适合资源库和内容平台的布局能力，不保留 SaaS 套餐转化结构。
8. V1 产品定位：一站式出海资源平台是核心，博客和关于我是辅助模块。
9. 社区能力：V1 只做投稿、纠错、补充信息和外部讨论入口，不做站内评论和完整社区。
10. AI 入口：定位为 AI Web SaaS 建站资源助手，而不是泛泛的全站聊天机器人。
