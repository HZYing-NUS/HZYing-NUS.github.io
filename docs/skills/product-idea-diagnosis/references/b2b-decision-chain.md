# B2B 决策链

## 适用场景

用户讨论企业 SaaS、采购、预算审批、大客户或多人决策时使用。

## 四类角色

| 角色 | 核心问题 |
|---|---|
| 使用者 | 谁每天使用，当前工作哪里最痛 |
| 决策者 | 谁判断是否值得引入，承担什么业务结果 |
| 付费方 | 谁批准预算，如何判断投入产出 |
| 阻止者 | 谁可能因安全、法务、财务或流程风险否决 |

角色可以重合，但必须落到具体公司、具体岗位和可验证的真实对象。职位名称只能描述角色，不能替代用户证据。

## 诊断顺序

1. 先确认使用者最近一次遇到问题的具体场景；
2. 记录使用者当前如何处理以及付出的代价；
3. 确认决策者希望改善的业务指标；
4. 确认付费方的预算来源与审批门槛；
5. 确认阻止者最担心的风险和所需证明；
6. 判断同一价值主张能否至少说服其中两个角色。

不要一开始只分析组织结构。没有使用者的真实痛点，决策链再完整也不能证明需求成立。

## 购买理由

把品类描述改写为可购买的结果：

```text
为谁
＋在什么触发场景下
＋完成什么具体动作
＋产生什么可衡量结果
＋需要多长时间
＋如何收费
```

例如，不说「企业培训平台」，而说「在下一次审计前，帮助 300 人完成指定培训，并交付完成率和留痕材料」。数字、时间和价格必须来自实际方案，不得编造。

## 第一轮销售验证

优先访问创始人能够直接触达的真实从业者，询问过去发生过什么：

> 最近一次遇到这个问题是什么时候？当时谁负责？怎么解决？花了多少时间或预算？

不要先展示 Demo 后询问「有没有兴趣」。礼貌反馈不是购买证据。

## 危险信号

- 只描述公司规模，无法说出第一批可触达的公司；
- 产品做完后才考虑销售和审批；
- 使用者喜欢，但付费方没有预算或收益依据；
- 忽略安全、法务、数据和集成风险；
- 把「有兴趣」当作采购承诺。

## 下一步

补齐一条真实决策链，分别记录四类角色的目标、反对意见和成功标准，然后再决定做产品还是先交付服务。
